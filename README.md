# شب‌های مافیا — Night War Event

> یک تجربه‌ی سینمایی از اعتماد، تردید و انتخاب.

این مخزن، **نسخه‌ی مرجع پروژه‌ی Night War** است. از این فایل به بعد، تصمیم‌های فنی، ساختاری و بصری پروژه باید روی همین پایه انجام شوند؛ ساختار اصلی بدون دلیل موجه تغییر نمی‌کند.

---

## ایده‌ی پروژه

**Night War** یک وب‌سایت معرفی و تجربه‌ی یک رویداد مافیایی است؛ اما قرار نیست شبیه یک داشبورد بازی یا یک سایت گیمینگ معمولی باشد.

هدف این است که کاربر هنگام ورود، بیشتر از اینکه «اطلاعات یک بازی» ببیند، وارد **فضای یک داستان جنایی سینمایی** شود.

سه واژه مسیر تجربه را تعریف می‌کنند:

**سینمایی · تنش · تردید**

تصویر، حرکت، نور و ریتم باید قبل از متن داستان را منتقل کنند.

---

## مسئولیت هر لایه

### HTML
`index.html` اسکلت و ترتیب تجربه را نگه می‌دارد. ساختار بخش‌ها باید قابل فهم و semantic بماند.

### Data
فایل‌های `data/roles.json` و `data/scenarios.json` منبع محتوای سناریوها و نقش‌ها هستند. اطلاعات بازی نباید بی‌دلیل داخل JavaScript تکرار شود.

### CSS
CSS به دو سطح تقسیم شده است:

- **Components:** اجزای قابل استفاده‌ی مجدد مثل Card، Button، Glass و Sheet
- **Sections:** ظاهر اختصاصی بخش‌های اصلی صفحه

توکن‌های مشترک در `tokens.css` قرار می‌گیرند تا هویت بصری در کل پروژه یکپارچه بماند.

### JavaScript
هر ماژول فقط یک مسئولیت مشخص دارد. تعاملات جدید باید تا حد امکان در ماژول مربوط به خودشان قرار بگیرند و `main.js` نقش هماهنگ‌کننده داشته باشد.

## قوانین طراحی

1. **Mobile First** اولویت مطلق است.
2. تجربه باید در موبایل با لمس و اسکرول طبیعی باشد.
3. متن کوتاه و کنترل‌شده باشد؛ تصویر و حرکت وظیفه‌ی اصلی روایت را بر عهده دارند.
4. Glass UI فقط جایی استفاده شود که ارزش بصری و عملکردی داشته باشد.
5. حرکت‌ها باید آرام، سنگین و سینمایی باشند؛ نه بامزه و جهنده.
6. هیچ صدایی در تجربه‌ی سایت وجود ندارد.
7. از 3D / WebGL / Three.js به پروژه اضافه نشود مگر اینکه تصمیم پروژه صراحتاً تغییر کند.
8. تصاویر نهایی ترجیحاً و در خروجی پروژه **WebP** باشند.
9. از تغییر بی‌دلیل معماری فایل‌ها خودداری شود.
10. هر قابلیت جدید باید با سیستم موجود هماهنگ باشد، نه اینکه یک سیستم جداگانه بسازد.

## سیستم حرکت

حرکت در Night War باید نقش روایی داشته باشد.

**قاعده:**

```text
حرکت ≠ تزئین
حرکت = بخشی از روایت
```

اسکرول باید حس ورود به یک صحنه‌ی جدید را ایجاد کند. برای تعاملات سنگین، اولویت با `transform` و `opacity` است و برای کارهای اسکرولی باید تا حد امکان از معماری سبک و بهینه استفاده شود.

در صورت فعال بودن `prefers-reduced-motion`، حرکت‌های غیرضروری باید کاهش پیدا کنند.

## وضعیت رسانه‌ها

ویدئوی Hero توسط تیم پروژه انتخاب و اضافه می‌شود.

مسیر استاندارد آن:

```text
assets/video/hero.mp4
```

ویدئو باید:

- بی‌صدا باشد.
- کوتاه و loop-friendly باشد.
- برای موبایل بهینه شده باشد.
- بدون ایجاد Layout Shift نمایش داده شود.

تصاویر سناریوها:

```text
assets/images/scenarios/
```

تصاویر نقش‌ها:

```text
assets/images/roles/
```

نام فایل‌ها باید ساده، انگلیسی، lowercase و قابل پیش‌بینی باشند.

## مسیر توسعه

### 01 — هویت و زیرساخت
قفل کردن توکن‌ها، تایپوگرافی، ساختار فایل‌ها و قراردادهای داده.

### 02 — Hero
اتصال ویدئوی سینمایی، لایه‌ی متن، کنترل نمایش روی موبایل و fallback مناسب.

### 03 — Story Experience
تقویت انتقال بین Introduction، Scenario و Story تا صفحه یک روایت واحد داشته باشد.

### 04 — Scenario System
بهبود کارت‌ها، انتخاب سناریو، آمار و انتقال به نقش‌ها.

### 05 — Role Experience
ارتقای Role Card و Role Sheet؛ اطلاعات مکانیک بازی دقیق بماند و ارائه‌ی آن سینمایی‌تر شود.

### 06 — About / Contact
پایان‌بندی آرام و مطمئن برای معرفی مجموعه و مسیر رزرو.

### 07 — Performance & QA
تست واقعی روی موبایل، کاهش CLS، بهینه‌سازی LCP/INP، lazy loading رسانه‌ها، دسترسی‌پذیری و reduced motion.

### 08 — Final Polish
ریزحرکت‌ها، فاصله‌ها، نور، کنتراست، تایپوگرافی و جزئیات نهایی.
